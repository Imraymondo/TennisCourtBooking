# 本机运行，接收真实短信

使用自己的电脑运行网站和SQLite数据库，通过ngrok临时HTTPS入口接收Twilio回调，无需部署网站或购买域名。`npm run sms:local` 同时允许电话和短信回调；原来的 `npm run phone:local` 仍然只允许电话回调。

临时隧道只转发经过认证的 `POST /api/webhooks/voice` 和 `POST /api/webhooks/sms`。网站首页、`/admin`、预约列表及邮件接口均不通过隧道公开。两种启动方式使用同一个项目中的本机数据库，不需要重新建库。

## 1. 确认本机配置和号码能力

- 复用已有 `.env.local` 中的 `TWILIO_AUTH_TOKEN`、`TWILIO_PHONE_NUMBER` 和 `NGROK_AUTHTOKEN`。已有电话功能可用时，不需要为短信重新申请一套凭据。
- Twilio号码必须具有 **SMS** 能力，并能在所选地区接收测试短信及发送回复；只有Voice能力的号码无法接收短信。号码能力可在Twilio控制台核对。
- 试用账号的收发号码验证、地区和测试限制，以Twilio控制台显示的要求为准。测试手机如需验证，请先在控制台完成。
- 首次使用本机流程时，按[本机电话说明](local-phone.md)安装依赖并配置ngrok。需要Node.js24.5以上的24.x版本，推荐24.22.1。

不要把Auth Token、ngrok Authtoken、完整手机号或预约管理码发到聊天中。不要覆盖现有 `.env.local` 或删除 `.data`；后者保存已有预约。

## 2. 停止旧服务，更新并启动短信模式

在原来运行 `phone:local` 或 `sms:local` 的终端按 **Ctrl+C**，停止本项目的旧服务和隧道，然后在同一个项目目录执行：

```bash
git pull
npm run sms:local
```

如果是首次安装，先执行 `npm ci --include=dev`。可用 `npm run phone:check` 检查必需配置的存在性和格式；预检不会显示密钥值，也不代表真实短信已开通。

命令会启动本机网站、检查数据库、建立临时HTTPS入口，并打印两条实际回调地址：

```text
Twilio Voice webhook (POST): https://…/api/webhooks/voice
Twilio Messaging webhook (POST): https://…/api/webhooks/sms
```

请使用终端本次输出的完整地址，不能把这里的省略号当成真实域名。脚本会将当前入口自动提供给应用用于Twilio签名校验，不需要手工改写 `.env.local` 中的 `APP_BASE_URL`。

保持电脑、终端和网络持续运行。Ctrl+C、电脑休眠或断网会使短信回调停止，本机预约数据仍保留。如果默认网页端口被占用，先停止本项目旧进程，或使用已有的 `PHONE_WEB_PORT` 配置；不要终止其他应用。

## 3. 更新Twilio号码的Messaging回调

打开Twilio控制台，进入 **Phone Numbers → Manage → Active numbers → 你的号码 → Messaging配置**：

1. **A message comes in** 选择 **Webhook**。
2. URL填写刚打印的完整 **Messaging** 地址，路径必须为 `/api/webhooks/sms`。
3. 请求方法选择 **HTTP POST**。
4. 保存。

这里设置的是收到短信时的回调，不是短信状态回调。已经配置过Messaging，也要核对是否仍为本次启动输出的地址：重新启动后隧道域名可能变化。若域名变化，同时将Voice的 **A call comes in** 更新为本次打印的Voice地址及HTTP POST，保留电话功能。

仅运行 `phone:local` 时，即使Twilio已经填写Messaging地址，短信路径也会被本机代理拒绝；要同时收电话和短信，应运行 `sms:local`。不要用公开网页、后台地址或本机回环地址作为Twilio回调。

## 4. 用自己的手机按顺序验证

默认短信使用下列固定格式指令。命令、日期、场地和时段之间用空格分隔；姓名不含空格。日期使用 `YYYY-MM-DD`，时间为悉尼时间的整点，时长省略时默认2小时。

也可按[OpenAI配置说明](openai-booking.md)启用GPT理解预约自然语言。该模式会逐步收集缺失信息，自然语言创建、修改和取消在复述后需另发明确确认；固定格式指令仍保持原有执行方式。两种模式都只处理预约事务。

下面的 `YYYY-MM-DD`、`预约编号` 和 `管理码` 都是占位文字，发送前必须替换为真实值。选取悉尼当前日期之后的一天，并先查询空档；不要直接发送占位文字。

### 帮助和查询

先向Twilio号码发送：

```text
帮助
```

收到指令说明后，查询一个未来日期：

```text
查询 YYYY-MM-DD
```

不填写场地时查询两片场地；也可发送 `查询 YYYY-MM-DD 1 2`，查询一号球场可连续预约2小时的开始时间。

### 创建测试预约

确认一号球场所选日期的08:00可以连续预约2小时后发送：

```text
预订 1 YYYY-MM-DD 08:00 短信测试 2
```

如果08:00不是实际空档，请替换为查询结果中的可用开始时间。系统会再次检查冲突，不能依靠旧查询结果覆盖别人的预约。

成功回复应包含场地、日期、时段、**预约编号**和**管理码**。请自行保存这两项，之后查看、修改和取消都需要它们。姓名“短信测试”会显示在公开日程上，发送短信的手机号码不会公开显示。

打开本机3000端口的网页（设置过 `PHONE_WEB_PORT` 时使用对应端口），选择短信中的同一日期并刷新，应看到新预约。已打开的网页也会每30秒自动更新；不要打开隧道域名查看首页，隧道只接收允许的回调。

### 修改、查看和取消

先查询目标日期和时段，确认空闲，再使用收到的编号和管理码发送，例如将预约改到二号球场14:00、仍为2小时：

```text
修改 预约编号 管理码 2 YYYY-MM-DD 14:00 2
查看 预约编号 管理码
```

修改成功后，在本机网页选择相应日期并刷新；原时段应释放，新时段应出现预约。测试完成后取消测试预约，避免留下占用：

```text
取消 预约编号 管理码
```

收到“已取消”回复后刷新网页，测试预约应不再占用原时段。取消记录会保留在工作人员后台。

## 5. 没有回复时如何定位

先确认本机终端仍在运行 `sms:local`，再对照Twilio控制台中的 **Messaging Logs**（界面中也可能显示为 **Monitor → Logs → Messaging**）检查同一时间的入站与出站记录。

| 观察结果                          | 下一步检查                                                                                                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 没有入站记录                      | 确认短信发送到具有SMS能力的Twilio号码、地区支持及试用账户测试号码验证要求                                      |
| 有入站记录，但回调失败            | 查看回调的HTTP方法、完整URL、HTTP状态和Twilio错误码；核对本次终端输出的最新地址及POST方法                      |
| HTTP404或405                      | 检查是否误用 `phone:local`、路径是否为 `/api/webhooks/sms`，以及方法是否为POST；首页和其他路径被拒绝是预期行为 |
| HTTP403                           | 核对当前号码所属账号的Auth Token、接收号码和签名所用地址；重启本机脚本后使用它刚输出的地址，不要关闭签名校验   |
| HTTP5xx、超时或Twilio11200        | 检查本机服务和ngrok连接、电脑休眠状态、最新代码及终端错误码                                                    |
| 回调为HTTP200，但手机没有收到回复 | 检查出站Messaging记录的状态、错误码、目标地区和试用账号限制；HTTP200只说明回调被接收，不等于手机已收到短信     |
| 收到格式或时段错误回复            | 使用“帮助”中的固定指令；替换未来日期和实际空档，确保时间为整点，并提供正确编号和管理码                         |

需要协助时，只提供大致测试时间、入站/出站状态、回调HTTP状态及脱敏错误码即可。不要提供密钥、完整手机号、管理码或含客户信息的短信原文。

## 已验证与待验证的范围

本项目的自动化测试使用本地模拟回调，检查允许的路径、原始请求、Twilio签名验证及预约数据处理，不会发送真实短信。自动化通过不表示你的号码、隧道和手机收发链路已经开通。真实短信的帮助、查询、预订、修改和取消流程，需在自己的电脑配置账号后按以上步骤完成验证。
